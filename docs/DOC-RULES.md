# Правила ведения документации

Этот файл главнее привычек. Если документ не описан здесь — его не заводим.

## Почему так

Документация проекта разрослась до ~692 КБ в 32 файлах. Виноват жанр: журналы
писались повествованием, а оно растёт от времени работы, а не от сложности
решения, и не имеет естественного конца. Заменяем жанр на записи фиксированной
формы с лимитом. Строку в 200 символов раздуть невозможно.

Файл без жёсткой формы ползёт обратно в рассказ сам собой: в плане заводятся
пояснения к пунктам, в контексте — пересказ реестра, в конце плана — раздел
«долги» из абзацев без галочек. Любая такая строка принадлежит одному из трёх
жанров ниже и едет туда, а не остаётся на месте.

## Где что живёт

| Файл                         | Что внутри                                       | Когда меняется                       |
| ---------------------------- | ------------------------------------------------ | ------------------------------------ |
| `docs/PROJECT-MAP*.md`       | Как устроен проект: структура, связи, инварианты | При изменении структуры кода         |
| `docs/DECISIONS.md`          | Решения дольше одной версии: строка на решение   | Когда решение переживёт версию       |
| `docs/CODE-STYLE.md`         | Правила кода и комментариев                      | Редко                                |
| `docs/<версия>/PLAN.md`      | План работ и отчёт по нему                       | При смене плана и по закрытии пункта |
| `docs/<версия>/CONTEXT.md`   | Суть текущего шага                               | Перезаписывается целиком каждый шаг  |
| `docs/<версия>/DECISIONS.md` | Решения этой версии в той же форме               | При каждом решении версии            |

В версионной папке до трёх файлов и ни одним больше. Пока своих решений у
версии нет, её реестра не существует и файлов два, как в `docs/2.0.0/`.
Четвёртого не появляется никогда: если материалу тесно — он либо решение
(в реестр), либо устройство (в карту), либо развёрнутое «почему» (в тело коммита).

## Тело коммита — основной носитель «почему»

Заголовок, пустая строка, 3–8 строк объяснения: что не так было, почему выбрано
это решение, что отвергнуто. Текст привязан к диффу, не устаревает и ищется
(`git log -S 'FLUSH_TIMEOUT_MS'`, `git show <хеш>`).

Однострочные сообщения вида `style: правки` обесценивают реестр: по такому хешу
копать нечего.

## Реестр решений

Одна строка, четыре поля через `·`:

```
2026-08-06 · net-check: пробы последовательно · 429 у Shikimori при веере · 5c31645
```

Дата, предмет, причина до 15 слов, хеш. Никаких абзацев и подразделов.
Отменённое решение не стирается: добавляется новая строка со словом «отменяет»
и хешом прежней.

Реестров два, форма записи у них одинаковая. Решение про устройство проекта,
жизненный цикл, живые ограничения и правила работы идёт в общий реестр;
решение про возможность, которая делается сейчас, — в реестр своей версии.
Версионная запись вправе отменить общую, обратное неверно.

Упёрся в потолок — решается по-разному. Версионный реестр не делится
никогда: его переполнение значит, что версия либо готова к релизу, либо
вместила в себя две. Общий реестр делится по предмету на `DECISIONS-<предмет>.md`
в корне `docs/`, со ссылкой из главного; сокращать или чистить его нельзя.

## PLAN.md

Пункт — строка с галочкой. Закрыли пункт — ставим `[x]` и дописываем хеш в конец
строки. Отдельного отчёта нет: план с галочками и есть отчёт, и он не может
разойтись с планом.

```
- [x] 5.3.7 Сторож прокси при аварийном выходе · 5a3ea87
- [ ] 5.4 Движок фильтров вместо ручных списков
```

Подробности пункта — в коммитах пункта. В плане их нет: ни вложенных
пояснений под строкой, ни разделов из абзацев. Незакрытое тоже живёт
пунктом с пустой галочкой, включая вопросы к владельцу и замороженные пункты.

## CONTEXT.md

Рабочий буфер: где остановились, что проверено, что делать следующим шагом.
Перезаписывается целиком, историю не копит. Лимит 40 строк. Пустой файл —
нормальное состояние между задачами.

Чего в нём не бывает: пересказа записей реестра и списка сделанного с хешами —
первое есть в реестре, второе в плане. Ссылка на них короче и не расходится.

## Лимиты

| Что                  | Потолок      |
| -------------------- | ------------ |
| `PLAN.md`            | 8 КБ         |
| `CONTEXT.md`         | 40 строк     |
| Любой `DECISIONS.md` | 15 КБ        |
| Файл карты проекта   | 18 КБ        |
| Строка решения       | 200 символов |
| Раздел карты         | 1 экран      |

Потолок карты взят не из вкуса: выше него запись файла целиком через API
начинает рваться. Переросшая карта делится по слою, как уже было сделано
с модулями и оболочкой.

Версионный файл сверх потолка — признак сползания в рассказ, а не большой
версии.

## Чего в документации не бывает

- Пересказа кода словами: код читается быстрее пересказа и не устаревает.
- Размеров файлов и числа строк: устаревают от каждого коммита.
- Истории итераций «сначала сделали так, потом переделали»: это git.
- Ссылок на номера строк чужого кода и на строки монолита.
- Статусов и дат внутри текста: статус — галочка в плане, дата — в git.
- Новых файлов временного назначения: временное живёт в `CONTEXT.md`.

## Как писать через API

Правило одно: файлы держим меньше потолка и после каждой записи перечитываем
написанное. Почему именно так — три строки раздела «Работа с репозиторием»
в `docs/DECISIONS.md`.

Если буква портится дважды подряд — фразу переформулируют так, чтобы спорного
символа в ней не было вовсе. Почему именно так — см. там же.
