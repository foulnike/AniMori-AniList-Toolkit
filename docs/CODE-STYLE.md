# Стиль кода

## Комментарии — ОЧЕНЬ ЛАКОНИЧНЫ

Главное правило проекта. Читать до начала любой правки.

### Лимиты

| Место                                    | Потолок  |
| ---------------------------------------- | -------- |
| Шапка файла                              | 3 строки |
| Док-комментарий функции, типа, константы | 2 строки |
| Комментарий внутри кода                  | 1 строка |

Потолок — это потолок, а не норма. Большинству мест хватает одной строки
или нуля. Строка — это строка до 100 символов, а не абзац без переносов.

### Жёсткие запреты

Нарушение любого из них — повод переписать комментарий, а не искать оправдание.

1. Ни одного комментария из двух абзацев. Пустая строка `//` или `///`
   внутри комментария запрещена: она всегда значит, что лимит превышен.
2. Одна мысль на комментарий. Два довода — значит, второй идёт в `docs/`.
3. Никаких «Пункт 4.5», «Правка после...», «Статус на дату». Номера пунктов
   живут в плане версии, история правки — в теле коммита.
4. Никаких обращений к читателю и пересказа альтернатив: вместо «можно было бы X,
   но мы выбрали Y, потому что...» — одна строка с последствием.
5. Комментарий не длиннее кода, к которому относится.
6. Комментарии внутри встроенных JS-скриптов и шаблонов подчиняются тем же лимитам.

### Как умещаться

Не «сокращать текст», а оставлять одно: что сломается, если сделать иначе.

Плохо (11 строк): рассказ про чужой iframe, историю охоты, триста источников
и выбор канала связи.

Хорошо (2 строки):

```rust
/// Собирает адреса во вложенных фреймах по команде __animoriNetProbeArm.
/// В главном кадре молчит: триста рекламных бирж выбирают потолок за секунды.
```

### Что комментируем

Только неочевидное «почему»: ограничение платформы, обход дефекта, причина
странного порядка вызовов, цена решения.

### Что не комментируем

- Пересказ кода словами.
- Историю решений и отвергнутые варианты — им место в реестре решений.
- Рассуждения, аргументы, самооправдания.
- Повтор того, что уже сказано в шапке файла.

### SCSS

Разделители секций в `style.scss` — единственное исключение из лимитов:
они остаются. Стили одним файлом без функций и сигнатур иначе
не навигируются (решение `da4823a`).

Остальное в SCSS живёт по общим правилам: шапка файла до трёх строк, пояснение
к правилу — одна строка и только про неочевидное: борьба с разметкой AniList,
порядок слоёв, вынужденный `!important`.

## Переносы строк — за Prettier

Формат вручную не придумываем: любая правка заканчивается `npx prettier --write`
по затронутым путям, и только потом коммит.

Неочевидное место: свойство со списком значений через запятую Prettier всегда
разбивает построчно, даже короткое. Так живут `transition` и `font`
в `NavPanel.vue`: перечисление шрифтов занимает пять строк вместо одной.

Прецедент: два коммита подряд (`c588524`, `8840001`) ушли на угадывание этого
переноса вслепую. Правка чистого формата — работа того, у кого Prettier
запускается, а не того, кто видит только текст файла.

### Зачем

К 5.3.7 комментарии заняли около 40% веса исходников. Следствия:

1. Файлы упёрлись в порог 25 КБ, после которого перезапись через API рвёт текст
   на середине (случай `proxy.rs`, коммит `e5e109a`).
2. Логику приходится дробить по файлам не по смыслу, а по весу.
3. Файл перестают читать целиком, и правки идут вслепую.

### Прецедент

Первая редакция правила давала доку 3 строки и не запрещала абзацы. При чистке
`lib.rs` (коммит `876fa5a`) док `NET_PROBE_SCRIPT` вышел на 11 строк через четыре
абзаца — формально «по три строки каждый». Отсюда запрет № 1.

### Сплошная чистка пройдена

Весь код прошёл через эти лимиты партиями, их хеши — в истории ветки.
Повторных прогонов не делаем: дальше правило действует на каждую новую
строку, а старые места подтягиваются при ближайшей содержательной правке.
