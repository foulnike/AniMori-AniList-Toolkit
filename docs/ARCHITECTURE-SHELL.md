# Архитектура: оболочка и сборка

Часть документа «Архитектура». Обзор, слои, мост, слой запросов и хранение —
в `ARCHITECTURE.md`; экраны и надстройка — в `ARCHITECTURE-UI.md`; видео и плеер —
в `ARCHITECTURE-VIDEO.md`.

---

## Окна двух родов

Окно `main` грузит свою сборку из `dist/app` — это локальный фронтенд.
Окно `site` — браузер одного сайта: живой anilist.co со встроенной
надстройкой, запасной вид на время неполных своих экранов. Окно `login`
держит форму входа.

Отсюда три следствия:

1. оба окна создаются кодом, а не в `app.windows` конфига: окну с сайтом
   нужны внешний адрес и скрипты инициализации;
2. разрешения разведены: `capabilities/default.json` для своего окна,
   `capabilities/site.json` для окна с чужим доменом;
3. внешние ссылки перехватываются в `on_navigation` и уходят в системный
   браузер: иначе окно уехало бы на сторонний сайт без адресной строки.

Бандл и стили надстройки вшиваются в двоичный файл через `include_str!`
из `dist/`. Поэтому `npm run build:tauri` обязателен до `cargo`: без бандла
сборка Rust падает на чтении файла.

## Вход

Вход AniList идёт без системного браузера: форма открывается в окне
с меткой `login`, которое идёт через наш прокси. Сайт недоступен из РФ,
а нашего прокси внешний браузер не знает.

Пропуск возвращается на `http://127.0.0.1:48513/relay`. Приёмник слушает
только петлю, сам отдаёт страничку-стрелочник и гаснет через пять минут.
Разметка видит только факт входа и срок, сам пропуск в неё не попадает.
Ручная вставка — запасной путь, если возврат не дойдёт.

**Адрес возврата задан не в репозитории.** Запрос авторизации посылает
только номер клиента и тип ответа; куда именно AniList вернёт пропуск,
определяет поле адреса возврата в консоли разработчика на стороне AniList.
Из кода этого не видно и код этого не проверяет. Значит, при смене адреса
приёмника правится консоль, а не исходник, и расхождение выглядит
как «вход не работает» без единой ошибки в журнале. Это единственная
настройка проекта, живущая за его пределами, и потому её стоит
перепроверять при каждом разбирательстве со входом.

Окна создаются только из рабочего потока, поэтому все команды открытия
асинхронные: в главном потоке `build()` ждёт сам себя.

## Прокси

Трафик десктопа идёт двумя независимыми каналами, и прокси настраивается
для каждого своим способом: страница — через ключи запуска WebView2,
запросы из Rust — через опцию клиента. Ключи WebView2 читаются один раз
при создании первого окна, поэтому решение о прокси принимается до него,
а смена настройки требует перезапуска.

`proxy.rs` сводит всё к одному из четырёх исходов: выключено, неверные
данные, адрес не отвечает, применено. Исход отдаётся интерфейсу командой:
молчаливое применение нерабочего прокси выглядит как поломка приложения.

`proxy_auth.rs` подставляет логин с паролем на событие базовой авторизации
WebView2, только под Windows: ключом запуска их не передать, а без
обработчика запрос отменяется молча. Событие одно и на 407 от прокси,
и на 401 от сайта, поэтому адреса из списка исключений пропускаются,
а число попыток подряд ограничено: кода ошибки в событии нет, и повтор
считается признаком неверного пароля.

`proxy_guard.rs` страхует от случая, когда прокси убивает страницу,
а выключается только в настройках внутри неё: без отметки готовности
прокси снимается и приложение перезапускается без него.

Пароль прокси лежит в файле настроек открытым текстом. Шифрования нет.

**Формулировки.** Ни одного адреса прокси в коде нет — человек вводит свои
данные сам, а мы предоставляем настройку сети. В интерфейсе и документации
это и описывается так: настройка соединения, без объяснений, что и как ею
обходится. То же касается зеркал Шикимори — домен `.rip` называется просто
адресом источника. С сентября 2025 года реклама и популяризация средств
обхода блокировок наказуемы административно, и нейтральная формулировка
здесь — дешёвая страховка, а не самоцензура. Функциональность от этого
не меняется ни на строку.

## Сборка

Три режима Vite. У `userscript` и `tauri` точка входа —
`src/userscript/main.ts`; у `app` свой корень `src/app` и выход `dist/app`.

|                 | userscript                      | tauri                            |
| --------------- | ------------------------------- | -------------------------------- |
| `@bridge-impl`  | `shared/bridge/MonkeyBridge.ts` | `shared/bridge/TauriBridge.ts`   |
| `@adblock-impl` | `shared/adblock/impl.noop.ts`   | `shared/adblock/impl.desktop.ts` |
| Формат          | сборка с шапкой юзерскрипта     | IIFE, без динамических чанков    |
| CSS             | встраивается в скрипт             | отдельный файл, вшивается в Rust |
| Очистка `dist`  | да                              | нет                              |

Сборка Rust требует обоих выходов. Порядок: `build:tauri`, `build:app`,
`cargo`.

Минификация выключена намеренно: правила Greasy Fork требуют читаемого
исходника. Динамический `import()` запрещён — в юзерскрипте ему неоткуда
грузить чанки. Обе причины прямо влияют на выбор библиотеки для плеера.

Номера версий обоих продуктов живут в `versions.json` и берутся
по продукту, а не по среде: скрипт в окне Tauri — тот же скрипт.
Расхождение с номером в `package.json` роняет сборку нарочно. Теги выпуска
идут с приставкой продукта: `script-2.0.2`, `app-3.0.0`.

### Разделение двух продуктов

Сейчас оба продукта делят не только ядро, но и настройки с типами.
После снятия манги из приложения в общем коде остались вещи, нужные
только юзерскрипту: ключи `enableLinkMangalib` и `mangalibDomain`, регэкспы
глав и томов в `core/constants.ts`, тип `MediaType`, раздел манги в поиске
персон и поле томов в типах сравнения списков. Всё это подписано
комментариями в коде именно потому, что без объяснения следующая чистка
снесёт его «за компанию» и сломает выпущенный скрипт.

Порядок разделения важен: сначала свои экраны замещают надстройку
по возможностям, и только потом общий код режется надвое. Иначе
юзерскрипт останется без части ядра раньше, чем приложение научится
делать то же самое.
