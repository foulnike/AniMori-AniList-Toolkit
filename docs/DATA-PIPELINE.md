# Датасет названий

Как массовые данные переезжают из рантайма в заранее собранный файл.

Статус: спроектировано, не реализовано.

---

## Зачем

Сейчас каждое русское название при первом показе — сетевой запрос.
Список на сотню записей при потолке 60 запросов в минуту раскрашивается
около двух минут. На втором запуске выручает кэш, но первое впечатление
уже испорчено, а на новом устройстве всё повторяется с нуля.

Вторая причина важнее первой. Любой из чужих сервисов может уйти в 403
без предупреждения — августовская отключка AniList держалась три дня.
Файл, лежащий на диске, в 403 не уйдёт.

Датасет — ускорение и страховка, а не единственный путь. Сетевой путь
остаётся живым для всего, чего в файле не оказалось.

---

## Что мешает прямо сейчас

**`resolveTitle` отдаёт название и описание одним запросом.**

В `api/titles.ts` один вызов возвращает сразу имя, описание, ссылку,
имя источника, оценку и распределение голосов. Сетка списка и открытая
карточка ходят в одну и ту же функцию, хотя сетке нужно только имя.

Следствие: если просто положить имена в датасет и ничего больше
не трогать, запрос на каждую карточку останется — ради описания,
которое в сетке даже не показывается. Выигрыш будет нулевой.

Поэтому первый шаг всего переезда — разделить функцию на две:

- `resolveTitle(malId)` — только имя, сначала из датасета, потом из кэша,
  потом из сети. Этот путь обслуживает сетки и полки.
- `resolveDescription(malId)` — описание и всё остальное, только сетью
  и только при открытии карточки.

Правка затрагивает `MediaScreen.vue` — файл на 45 КБ, самый крупный
в проекте и самый переполненный. Разрезать его надо до этой работы,
а не во время неё.

## Что едет в датасет, а что нет

| Данные                      | Как нужны        | Где живут        |
| --------------------------- | ---------------- | ---------------- |
| Русские названия аниме      | сотнями сразу   | датасет          |
| Соответствия MAL — AniList  | пачками         | датасет          |
| Год, тип, оценка           | вместе с именем | датасет          |
| Описания                    | по одному       | сеть            |
| Персонажи и авторы          | десятками       | вторая очередь   |
| Обложки                     | по одной        | сеть, никогда не в файл |

Правило отбора одно: **в датасет едет то, что нужно сотнями сразу.**
Один запрос на одно открытие карточки человек переживёт. Сотня запросов
на открытие списка — нет.

Манга не едет вообще: она снимается из продукта. Это сокращает файл
почти вдвое и снимает необходимость во втором источнике.

## Где брать данные

### Соответствия идентификаторов: готовая база

`manami-project/anime-offline-database` — около 32 тысяч тайтлов со связками
номеров между MAL, AniList, Kitsu и прочими. Обновляется еженедельно,
выпуски помечены как `ГОД-НЕДЕЛЯ`. Есть урезанный срез только с AniList
на сотню килобайт в сжатом виде — ровно то, что нужно.

Лицензия ODbL-1.0. Она требует указания источника и сохранения той же
лицензии на производную базу. Проект под MIT, поэтому датасет лежит
отдельно со своей лицензией, а не внутри репозитория приложения.
Это не формальность: смешать ODbL с MIT в одном дереве — значит создавать
непонятно что для того, кто захочет форкнуть.

### Русские названия: свой обход Шикимори

Готовой открытой базы русских названий нет. Собирается самостоятельно.

У Шикимори есть выписка пачкой: `GET /api/animes?ids=1,2,3,...&limit=50`.
Пятьдесят тайтлов за один запрос. Тридцать две тысячи тайтлов — около
640 запросов. При паузе 700 мс это около семи с половиной минут.

Ограничения сервиса: пять запросов в секунду и девяносто в минуту,
обязательный осмысленный `User-Agent` — без него ответ 429 или 403.
Пауза 700 мс вдвое мягче разрешённого, и это намеренно: обход идёт
раз в неделю ночью, торопиться некуда, а ссориться с единственным
источником кириллицы не хочется.

Из ответа берётся шесть полей: `id`, `name`, `russian`, `kind`, `aired_on`,
`score`. Остальное отбрасывается сразу: чем меньше в файле, тем быстрее
он грузится на слабом канале.

**Непроверенное:** запросы пойдут с адресов датацентра, а не с домашних.
Как на это смотрит Шикимори — неизвестно. Перед полным обходом надо
прогнать пробу на десятке пачек и посмотреть две вещи: не отдаётся
ли 403 с чужого IP и какая доля тайтлов вообще имеет русское название.
Второе важнее: если покрытие окажется низким, весь замысел надо менять.

### Замечание об источнике по умолчанию

Сейчас в `settings.ts` главный источник названий — **anime365**, а Шикимори
запасной. Датасет же строится по Шикимори, потому что только у него
есть выписка пачкой по номерам MAL.

Значит, после переезда человек увидит названия из другого источника,
чем видел до него. Названия у двух сервисов расходятся чаще, чем кажется.
Это надо решить осознанно, а не обнаружить после выпуска. После снятия
манги причина, по которой выбран текущий порядок, всё равно отпадает.

## Где собирать

Отдельный публичный репозиторий `foulnike/animori-data`. Отдельный — по трём
причинам: другая лицензия, другой ритм выпусков, и история кода не тонет
в еженедельных коммитах робота.

GitHub Actions для публичных репозиториев бесплатны и не тарифицируются.
Это не свой сервер: ничего не надо содержать, нет аптайма, нет счётов,
нет чужих данных. Задача либо отработала, либо нет, и в последнем случае
клиенты просто продолжают жить на предыдущем выпуске.

### Расписание

Раз в неделю по расписанию плюс ручной запуск кнопкой. Ручной запуск
обязателен: именно им отлаживаются правки, и он же спасает, когда
ночной запуск не состоялся.

Две ловушки расписания, обе документированы GitHub:

1. **Задача по расписанию отключается после 60 дней без активности
   пользователя в репозитории.** Коммиты, сделанные встроенным токеном
   самого робота, активностью не считаются. То есть робот, коммитящий
   сам себя, тихо умрёт через два месяца. Лечится личным токеном доступа
   вместо встроенного.
2. **Запуск по расписанию опаздывает на 10–30 минут**, а в час пик может
   быть пропущен вовсе. Для еженедельной задачи это безразлично,
   но рассчитывать на точное время нельзя.

Жёсткий предел: шесть часов на задачу. Обход названий укладывается
в восемь минут и запаса хватает стократно. Обход людей — нет,
и именно поэтому он делается срезами.

## Как поставлять

Артефакты кладутся в выпуск репозитория. Причины:

- Трафик на файлы выпусков не тарифицируется, потолок на файл — 2 ГиБ.
  Для наших единиц мегабайт это запас без конца.
- Старые выпуски остаются доступными. Клиент старой версии не ломается
  от того, что формат поехал вперёд.
- Загрузка идёт с `objects.githubusercontent.com`, который уже есть в списках
  разрешённых адресов обоих продуктов.

Зеркало через jsDelivr не подходит: оно не раздаёт файлы выпусков
и режет файлы крупнее 20 МБ. Оно годится только как запасной путь
для файлов из ветки.

### Состав выпуска

```
index.json              версия, дата сборки, список файлов, sha256
titles-anime.json.gz    русские названия и минимум полей
map-mal-anilist.json.gz соответствия номеров
people.json.gz          люди, вторая очередь, скользящими срезами
```

`index.json` — единственный файл, который клиент тянет на проверке.
Он маленький, и по нему видно, надо ли тянуть остальное. Хеши в нём нужны
не от злоумышленников, а от оборванной загрузки: половина архива,
распакованная в базу, — хуже отсутствия архива.

Файлы сжаты gzip, а не zstd: gzip распаковывается штатными средствами
браузера без сторонних библиотек. В юзерскрипте лишняя библиотека —
это лишние килобайты в файле, который читает модерация Greasy Fork.

## Как потреблять

Образец уже есть в коде: словарь интерфейса в `userscript/dictionary-remote.ts`
тянется с GitHub, кэшируется и при отказе откатывается к вшитой копии.
Датасет повторяет эту схему в большем масштабе.

Порядок на старте:

1. Читается версия датасета, лежащего на диске. Найден — работаем сразу.
2. Фоном, не блокируя ничего, тянется `index.json`. Не дошло — не беда.
3. Если версия новее — загрузка фоном, проверка хеша, замена целиком.
   Половинчатой замены не бывает.
4. Обновление применяется со следующего запуска. Менять имена под рукой
   у человека — нехорошо.

Порядок чтения имени становится четырёхуровневым: память запуска,
датасет, склад IndexedDB, сеть. Датасет выше склада, потому что он свежее
и полнее; склад остаётся для того, чего в датасете нет.

Где хранить распакованное — открытый вопрос. В десктопе есть подсистема
файлов с белым списком имён и потолком записи 8 МБ — оба списка
придётся расширить. В юзерскрипте остаётся только IndexedDB.
Развилка должна жить за мостом, а не в вызывающем коде.

## Порядок работ

1. Разрезать `MediaScreen.vue`.
2. Разделить `resolveTitle` на имя и описание. Без этого всё остальное
   бессмысленно.
3. Проба обхода: десяток пачек с руннера. Замерить покрытие кириллицей
   и проверить отношение к адресам датацентра.
4. Завести `animori-data`, собрать первый выпуск руками, посмотреть
   настоящий размер после сжатия.
5. Научить клиент читать датасет. Сначала только имена.
6. Поставить расписание и личный токен.
7. Люди — после того, как всё выше проработает месяц.

Шаги 1 и 2 — работа в существующем коде, без них нет смысла заводить
второй репозиторий. Шаг 3 может отменить всё остальное, поэтому он третий,
а не пятый.
